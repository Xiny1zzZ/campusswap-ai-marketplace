BUILDING CAMPUSSWAP

My project notes

What I have built so far, what is real, and what is still missing.

What I have built and who it is for

I am building CampusSwap for students who want to find affordable second-hand items for campus life. This is my initial marketplace MVP for the CognitioLabs Associate Forward Deployed Engineer assessment.

I have built a responsive catalogue, individual listing pages, category filtering, and one unified search box. I can enter an item name or describe what I need without choosing a technical search mode. Non-empty searches use the same semantic retrieval and return at most five listings at a tested 0.30 starting similarity threshold; an empty search shows the normal catalogue. Browse listing links preserve the current query and category, so a detail page can return me to the same results. I also built a separate Ask CampusSwap page where reviewers can ask factual questions and comparisons about the seeded catalogue. It uses a compact, responsive chat card with message bubbles, example questions, an in-card composer, and clickable cards for relevant catalogue items. When I follow one of those cards, Back to Ask CampusSwap restores the visible session conversation.

What is demo data

All 36 listings are seeded, fictional examples across study, electronics, furniture, sports, lifestyle, room essentials, books, and clothing. Names, conditions, prices, sellers, and Singapore pickup locations are examples, not verified offers from real students. The item pictures are emoji placeholders, not product photos. No sale, reservation, or conversation happens in this demo.

Tools and AI status

I used Codex to help inspect the repository, plan the architecture, write the application and documentation, and check the implementation.

The unified browse search and Ask CampusSwap both use openai/text-embedding-3-small through the CognitioLabs gateway to retrieve and relevance-order catalogue records. Ask CampusSwap then uses gpt-5.6-terra through the CognitioLabs OpenAI-compatible gateway to write its answer. The application reads the gateway key only from the server-side CLASSGW_KEY environment variable. The literal case-insensitive keyword API still exists, but people browsing the site no longer need to choose it.

Grounding and technical decisions

Ask CampusSwap is separate from both marketplace search modes. It sends the question and compact explicit SQLite fields for all 36 seeded listings to the answer model, after ordering them with the existing cached embedding retrieval. I intentionally use the full small catalogue rather than semantic Top-K context because questions about price or pickup location could otherwise miss the relevant listing.

The answer model returns concise text and candidate listing IDs. I treat those IDs as untrusted: the server checks each one is in the grounded context, reloads it from SQLite, and only then sends the real record to the browser as a clickable card. Cards show at most eight by default, or all validated matches when the question explicitly asks for all. Browse detail links reconstruct only local results URLs from whitelisted query and category fields. Ask uses sessionStorage only for visible questions, answers, validated cards, and the more-results state; it does not store the key, prompts, embedding vectors, scores, gateway details, internal errors, or backend chat history. I instruct the answer model to treat supplied catalogue records as its only source, compare only explicit values, and say when the seeded catalogue does not provide a requested fact such as warranty, delivery, or stock availability. This is a grounding design, not a guarantee against every possible adversarial prompt.

What I intentionally left out

I have not built accounts, authentication, payments, messaging, listing management, persistent chat history, streaming responses, or multi-turn server-side conversations. I also did not add a vector database, Vite, npm, a build step, or additional frontend libraries.

What I have checked

The automated Python tests use a temporary SQLite database and mock every embedding and chat-completion call, so they make zero real external gateway calls. They cover seed reconciliation, filters, validation, semantic caching and thresholds, Q&A context construction, comparison and missing-fact responses, and safe failures. I have not completed live browser or assistive-technology testing.

Known issues and current limitations

This is a local demo, not a deployed marketplace. There is no identity or campus verification, moderation, image upload, stock tracking, or real seller contact. SQLite needs a writable local disk; I have not designed this for multiple application servers.

Non-empty unified search and Ask CampusSwap need a valid server-side CLASSGW_KEY and gateway access. The 0.30 threshold, five-result cap, and full-catalogue Q&A context may need revisiting if the catalogue changes substantially. Ask CampusSwap has grounding instructions but no adversarial-prompt evaluation. There is no pagination, sorting control, deployment setup, or completed live accessibility review.
